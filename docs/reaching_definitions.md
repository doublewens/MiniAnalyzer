# 可达定义分析：数学定义、例题推导与解释（M3）

## 1. 教学目标与直观类比

**提问**：“走到第7条指令时，变量x当前使用的值*可能由哪一条赋值语句产生*？”

这里的“定义”指一条**静态IR赋值指令**，不是变量当前具体数值。例如`x@4`表示第4条指令对x的赋值。即使同一条指令在循环中执行多次，仍然对应同一个静态定义标识。

类比：班级里可能有多名学生将不同版本的文件放进同一个名为`x`的文件夹。某次覆盖写入会让该路径上之前的版本失效；不同分支汇合时则需要保留多个**可能的来源**。

这是**前向 may 分析**：只要存在一条CFG路径使某个定义到达程序点且途中未被同变量的其他定义覆盖，该定义就属于可达定义集合。它不证明某定义必然到达，更不直接证明变量的具体取值。当前IR中的条件真假并不被用来排除不可能执行的路径。

## 2. 抽象域与方程

记D为程序所有具有DEF的静态指令产生的定义标识的集合。数据流事实来自集合格：

- 抽象域 `P(D)`（D的幂集），偏序为`⊆`，底元素为空集。
- 路径合并：`join = ∪`，即可能定义取并集。
- 入口边界：空集（当前IR没有显式建模函数参数在入口处的定义）。
- 初始事实：所有程序点的IN、OUT从空集开始。

对于任何节点n：

```text
IN[n]  = union(OUT[p] for p in pred(n))  // 入口再并入边界
OUT[n] = GEN[n] union (IN[n] - KILL[n])
```

`GEN[n]`是指令n生成的定义，例如`x = x + 1`生成`x@n`；`KILL[n]`是整份程序中**其他指令**对相同变量的静态定义标识。对不定义变量的跳转、返回和无结果调用，GEN与KILL皆为空。由于D有限、各转移函数单调，从底开始迭代可达到不动点。

> 注意：`DataflowAnalysis.meet()`是历史接口名，本算法内执行的是集合并集，数学上应理解为上述偏序下的join。无需误认为“前向分析必用meet”。

## 3. 分支合并实例：rd_branch.ir

```text
1: c = call input()
2: x = 0
3: if c > 0 goto 6
4: x = 1
5: goto 7
6: x = 2
7: y = x + 1
8: return y
```

程序中的定义：`D={c@1,x@2,x@4,x@6,y@7}`。

| 节点 | 作用 | GEN[n] | KILL[n]（其他同变量定义） |
|---|---|---|---|
| 1 | 将调用返回值赋给c | `{c@1}` | `{}` |
| 2 | x=0 | `{x@2}` | `{x@4,x@6}` |
| 3 | 条件分支 | `{}` | `{}` |
| 4 | x=1 | `{x@4}` | `{x@2,x@6}` |
| 5 | 无条件跳转 | `{}` | `{}` |
| 6 | x=2 | `{x@6}` | `{x@2,x@4}` |
| 7 | y=x+1 | `{y@7}` | `{}` |
| 8 | 返回 | `{}` | `{}` |

从1进入，执行到2产生`x@2`。在3处分流：

- 走4→5：节点4杀死`x@2`并生成`x@4`，所以OUT[5]中有`{c@1,x@4}`。
- 走6：节点6杀死`x@2`并生成`x@6`，所以OUT[6]中有`{c@1,x@6}`。

在节点7汇合：

```text
IN[7] = OUT[5] ∪ OUT[6]
      = {c@1,x@4} ∪ {c@1,x@6}
      = {c@1,x@4,x@6}
OUT[7] = IN[7] ∪ {y@7}
       = {c@1,x@4,x@6,y@7}
```

**讲解要点**：`x@2`不存在于IN[7]，因为两个分支都重定义x；`x@4`和`x@6`均存在，表示“来源可能是第4条，也可能是第6条”，并不表示同一次执行会同时采用两个x值。

## 4. 循环不动点实例：rd_loop.ir

```text
1: x = 0
2: y = 2
3: if x >= y goto 6
4: x = x + 1
5: goto 3
6: return x
```

循环条件节点3存在两个前驱：节点2与节点5。定义：`D={x@1,y@2,x@4}`。

首次从入口方向传播：

```text
OUT[1] = {x@1}
OUT[2] = {x@1,y@2}
IN[3]  = {x@1,y@2}              # 暂时还未收到循环回边的定义
OUT[4] = (IN[4] - {x@1}) ∪ {x@4}
       = {x@4,y@2}
OUT[5] = {x@4,y@2}
```

当Worklist再次处理节点3时：

```text
IN[3] = OUT[2] ∪ OUT[5]
      = {x@1,y@2} ∪ {x@4,y@2}
      = {x@1,x@4,y@2}
```

这时循环头的x可能来自第1条初始化，也可能来自第4条循环体。由于下一轮不再产生新的静态定义，集合最终稳定：

```text
IN[3]  = {x@1,x@4,y@2}
OUT[4] = {x@4,y@2}
IN[6]  = {x@1,x@4,y@2}
```

**教学提问**：“为什么循环可能执行任意次，但IN[3]集合只包含两个关于x的定义？” 因为分析追踪的是**静态定义语句**，不是无限多次动态写入历史。有限域上的集合迭代终会达到不动点。

## 5. 连续覆盖及调用：rd_kill.ir

```text
1: x = 1
2: x = -x
3: x = call read(x)
4: call log(x)
5: return x
```

静态定义为`x@1`、`x@2`、`x@3`；执行到3时`IN[3]={x@2}`，执行后`OUT[3]={x@3}`。第4条没有结果变量，因此本分析不新增定义。当前教学IR的调用不会更改其他变量：这是简化语义，不等同于真实语言对副作用的分析。

## 6. 注意事项与适用边界

- 当前求解器保持v0.3逻辑：**对全部CFG节点求解，包括不可达节点**。因此不可达节点的事实可能影响可达节点；演示与练习应优先采用入口可达的示例。要分析真正的“程序可达语义”，下一阶段需专门设计仅从入口传播或不可达底值的策略，且要评估旧版兼容性。
- “路径不敏感”的分析不判断条件真值。因此可以把实际不可执行的CFG分支也纳入结果，导致保守的额外定义。
- 没有过程间调用、别名、指针或内存模型；赋值调用只定义其显式结果变量。
- 未建模函数入口参数和外部输入的抽象定义，也不追踪实际值。
- 这是经典数据流框架的学习案例，不是完整漏洞检测器。

## 7. 课内练习与参考答案

**练习A**：在分支例子里，把第6条`x=2`改成`z=2`，问节点7前x的可能定义？

**答案**：此时真分支不重新定义x，初始定义`x@2`可以沿着真分支到达7，假分支产生`x@4`；因此`IN[7]|_x = {x@2,x@4}`。

**练习B**：在循环例子里，为什么最终`OUT[4]`不保留`x@1`？

**答案**：因为执行节点4将x重新赋值，旧定义`x@1`被KILL，同时生成`x@4`。循环头可以保留两个可能来源，但循环体赋值后只保留本条对x的定义。

**练习C**：没有生成定义的`goto 3`会改变可达定义事实吗？

**答案**：不会。GEN、KILL均为空，其转移函数是恒等函数，但控制流回边可使其他节点重新入队计算。
